# 文档生命周期规范

## 适用范围

本规范用于管理项目中的长期维护文档和任务过程文档，包括目录职责、文件命名、元数据、执行状态、长期沉淀与任务归档。

## 目录职责

注意以下目录是以项目目录为根目录，不是skill所处目录。

- `docs/` 只保存当前有效的长期维护知识，例如架构、功能、数据模型、接口、部署、维护手册和稳定约束。不得写入任务进度、临时结论、实施流水或 AI 推理过程。
- `spec/` 只保存当前活跃任务的过程文档，例如需求澄清、分析、设计、计划、阶段记录和结果摘要。
- `spec/archive/` 保存已完成、已取消或已被替代任务的过程文档。归档目录保持扁平，不按年份或主题新增子目录。
- 只涉及一个项目的过程文档放在对应项目；同时涉及两个及以上项目的过程文档放在聚合项目顶层。

## 文件命名

- 过程文档统一命名为 `YYYYMMDD-<topic>-<type>.md`。
- 日期使用任务启动日期；同一任务共享相同的日期和主题前缀。
- `<topic>` 可使用中文或英文，但不得包含空格；英文使用小写 kebab-case。
- `<type>` 只能使用：`requirement`、`analysis`、`design`、`plan`、`record`、`result`。
- 不使用 `final`、`latest`、`new`、`v2` 等含义不稳定的名称；版本变化由 Git 历史和元数据表达。
- 文件归档时保持原文件名，不追加完成状态或归档日期。
- 长期文档使用稳定语义名，默认不带日期；只有内容本身以时间为主题时才使用日期。

## 过程文档元数据

所有 `spec/**/*.md` 必须以 YAML Front Matter 开头，并至少包含：

```yaml
---
title: 文档标题
document_type: design
document_status: draft
execution_status: not_started
task_id: 20260710-example-task
created: 2026-07-10
updated: 2026-07-10
scope:
  - project-name
---
```

- `title` 与正文一级标题一致。
- `document_type` 与文件名 `<type>` 一致。
- `task_id` 由日期和主题组成，同一任务的全部文档保持一致。
- `created` 首次创建后不得修改；`updated` 仅在内容实质变化或状态变化时更新。
- `scope` 使用项目目录名；跨项目任务列出所有相关项目。
- 可选字段 `related` 用于关联长期文档或同任务文档。

文档状态 `document_status` 只能使用：

- `draft`：草案，尚未确认。
- `confirmed`：已确认，可作为执行依据。
- `archived`：已结束使用，并已移入 `spec/archive/`。

执行状态 `execution_status` 只能使用：

- `not_started`：尚未开始执行。
- `in_progress`：正在执行。
- `blocked`：存在明确阻塞条件，暂时无法继续。
- `completed`：范围内工作及必要验证均已完成。
- `cancelled`：任务已明确取消。

同一 `task_id` 下的活跃文档必须保持相同的执行状态。阻塞时必须在正文记录阻塞原因、已完成范围和恢复条件；取消时必须记录原因。

## 执行标记

- 任务清单只使用标准 checkbox：`- [ ]` 表示未完成，`- [x]` 表示已完成。
- 不使用 `[~]` 等自定义 checkbox 表达进行中或阻塞；阶段整体状态以 YAML 为准，特殊情况写入任务正文。
- `completed` 状态不得存在仍属于交付范围的未完成项。范围外的后续建议应单独标记，不能与必做任务混淆。

## 创建与维护

- 用户明确要求方案或计划，或任务涉及多步骤、高风险、跨会话跟踪、需要跨项目协调时，应创建过程文档；仅同时修改多个项目不构成创建过程文档的理由，契约明确、改动紧密关联且可一次完成的前后端联动仍可按简单任务处理。
- 按任务需要创建文档，不要求机械地凑齐全部类型。
- 未确认的设计或计划使用 `draft`；用户确认后改为 `confirmed`；开始实施时改为 `in_progress`。
- 执行期间只记录影响后续工作的决策、范围变化、阻塞和验证结果，不记录逐条命令输出、重复对话或推理草稿。
- 设计发生实质变化时先更新设计，再同步实施计划。

## 任务结束、沉淀与归档

任务结束时依次执行：

1. 完成范围内验证，确认没有影响交付的未完成项。
2. 判断是否产生需要长期维护的知识；优先更新现有 `docs/`，没有合适文档时再创建新文档。
3. 长期文档只描述最终有效状态，不复制需求讨论、方案比较、实施步骤或历史流水。
4. 更新计划 checkbox 和执行状态；复杂任务可创建 `result`，简单任务可直接在 `plan` 中增加结果章节。
5. 将同一 `task_id` 的全部过程文档整组移入 `spec/archive/`，把 `document_status` 改为 `archived`，并填写 `archive_reason`。
6. 修复因移动产生的相对链接，并再次检查长期文档与当前实现一致。

`archive_reason` 只能使用 `completed`、`cancelled` 或 `superseded`。文档被替代时可填写 `superseded_by`；被替代文档允许先于同组其他文档单独归档。

部署或人工验收如果属于本次交付条件，未完成时任务必须保持 `in_progress` 或 `blocked`；如果明确不在执行范围内，可以完成当前任务，但必须记录外部后续事项。

归档文档原则上不再持续维护。后续事实变化应更新 `docs/`，新工作应创建新的 `task_id`。
